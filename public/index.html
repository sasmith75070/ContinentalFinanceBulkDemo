Use Case 1

Send a payment reminder

Continental Finance's core outbound program — payment reminders and past-due messaging. Whether the reminder is proactive (statement due in N days) or reactive (payment past-due), the mechanic is the same: personalized SMS to 3.5M cardholders per month with per-recipient delivery status and native scheduling, from a single API call.

Twilio Products used
  • Bulk Messaging API · POST /v1/Messages
    Actively invoked by the Send now button. One request accepts up to 10,000 recipients. Returns HTTP 202 + operationId.
    Docs ↗
  • Bulk Operations Resource · GET /v1/Messages/Operations/{id}
    Polled every 750ms after each send. Feeds the delivered / failed / unaddressable counters.
    Docs ↗
  • Scheduled sends · schedule.sendAt
    Actively invoked by the Schedule button. Up to 7 days out; omitting the timezone lets Twilio auto-localize to each cardholder's timezone.
    Docs ↗
  • Liquid variable substitution
    Actively used in the reminder template — {{firstName | default: 'Customer'}}, etc. Every recipient in the same call gets their own values.

What this proves

  • One API call, thousands of sends. POST /v1/Messages accepts a to[] array of up to 10,000 recipients.
  • Personalization is native. Liquid variables ({{firstName}}, {{amountDue}}) resolve per-recipient with default filter fallbacks.
  • Per-recipient status. The Operations resource returns Delivered / Failed / Unaddressable counters that advance in real time.
  • Native scheduling, up to 7 days out. Pass schedule.sendAt in the same API call. Omit the timezone and Twilio auto-localizes each cardholder's send time — so an 8am–9pm ET window becomes 8am–9pm local for every cardholder, without per-zone logic in Continental Finance's scheduler.

Use Case 2

Suppress reminders the instant a payment posts

Continental Finance's current ~15-minute lag between a cardholder's payment posting and their SMS provider knowing about it means paid-up cardholders still get past-due reminders. With a near-real-time payment webhook and the pending list re-read at the moment of each send, that lag drops to seconds.

Twilio Products used
  • Bulk Messaging API · POST /v1/Messages
    Same endpoint as Use Case 1. Called with the filtered list — recipients whose payment posted since the queue was built are excluded before the call fires.
    Docs ↗
  • Bulk Operations Resource · GET /v1/Messages/Operations/{id}
    Polled after send to confirm the suppressed cardholder's row shows no delivery attempt.
    Docs ↗
The payment webhook endpoint and the pending queue are Continental Finance's own integration, not Twilio products. Twilio's role in this use case is to accept the filtered list and deliver it — which is what makes the mechanic honest and simple.
1
A cardholder pays their bill Continental Finance's payment system POSTs to /webhooks/payment on our server with {phone, accountId, amount, postedAt}. No Twilio call in this step.
→
2
Our server suppresses that cardholder Server updates the pending queue: sets status = 'suppressed' for that phone. Still no Twilio call — the change lives in Continental Finance's data layer.
→
3
Send today's 10am reminder Server reads the queue for status = 'pending' at this moment, builds the payload, and POSTs to comms.twilio.com/v1/Messages. Twilio only ever sees un-suppressed cardholders.
Why this works: The Bulk Messaging API doesn't need a "cancel a recipient" endpoint because Continental Finance's server owns the recipient list until the moment of send. Every payment webhook that arrives before the send fires takes effect — no matter how close to send time. Continental Finance's 15-minute lag becomes their webhook-to-suppression latency, which is a millisecond problem.

    Use Case 3

    Every inbound message, captured and actionable

    Capture every cardholder response, handle STOP/START/HELP compliantly via Twilio-native automation (no code), route free-form text to a human review queue, and enforce app-side Do-Not-Contact suppression across every sender Continental Finance owns.

    Twilio Products used
    • Advanced Opt-Out · Messaging Service feature
      Actively demonstrated. Twilio auto-replies to STOP / START / HELP with custom Surge copy, updates its block list, and POSTs the event to our webhook with an OptOutType header for audit. No code.
      Docs ↗
    • Inbound Webhook · POST /webhooks/twilio/inbound
      Actively receives every inbound SMS — keyword-matched and free-form both. Free-form lands in the Ops Review Queue for a human.
      Docs ↗
    • Messaging Service
      Owns the Advanced Opt-Out configuration, the sender pool, and the inbound webhook URL. Console-managed.
